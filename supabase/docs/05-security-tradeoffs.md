# 05 — القرارات الأمنية والمقايضات

هذا الملف يوثّق القرارات المتبقية/المقايضات قبل التنفيذ، حسب طلب المراجعة.

## أ) رفع الملفات المجهولة (قرار مُتَّخذ ومُنفَّذ)

- **القرار:** لا رفع مباشر من `anon`؛ الحاوية خاصة، والتسليم حصريًا عبر
  Edge Function التي تستدعي `register_upload` ثم تُوقّع upload URL ثم تستدعي
  `confirm_upload` بصلاحيات `service_role`.
- **تطبيق أقل امتياز:** `register_upload` و`confirm_upload` **غير ممنوحتين لأي
  دور واجهة** (0011)؛ الواجهة تستدعي Edge Function فقط. البديل RLS بالـtoken
  **حُذف نهائيًا** (كان يسبّب MIME spoofing وDoS بلا فحص محتوى).
- **اتساق البيانات:** لم يعد `submit_response` يقبل `'pending'`؛ لا يُربط أي
  رفع إلا بعد تأكيد فعلي (`status='uploaded'`)، والحجم/النوع من الكائن الحقيقي
  في Storage (لا من إعلان المتصفّح).
- **وحيدية الإرفاق:** شرط `UPDATE ... WHERE response_id IS NULL AND status='uploaded'`
  يمنع إرفاق token واحد باستجابتين حتى مع طلبين متزامنين (سباق READ COMMITTED).
- **التنازل المتبقي:** يتطلب بناء Edge Function خارج SQL؛ لم يُنفَّذ بعد تنظيف
  تلقائي للحجوزات المنتهية (عنصر متابعة).

## ب) SECURITY DEFINER

القواعد المطبقة في كل دالة:
- `set search_path = ''` يمنع استغلال المسار بواسطة كائنات بالمخططات المعرّفة من المستخدم.
- كل المراجع مؤهَّلة بالكامل (`public.questions`, `app_private.foo`).
- `validate_answer_value` دالة استدعاء داخل `submit_response` ولا تُكشف لـ REST.
- `is_admin()` لا تأخذ معامل — تمنع فحص حالة مسؤول عشوائي (مصدر معلومات).
- صلاحيات EXECUTE: revoke من `public` ثم grant فقط للضرورة.
- **مقايضة:** كل دوال DEFINER تملك قدرة تجاوز RLS. لذلك:
  - تُعيد الحد الأدنى (void / JSON ثبّت).
  - لا تكشف `admin_users` ولا `responses` للواجهة.
  - `submit_response` لا تعيد هوية/معرف استجابة.
  - الكاتب يجب أن يكون المالك (postgres) — نُحقق ذلك داخل Project/SQL Editor.

## ج) ترقية/بحث API — التسوية مع RLS

- `submit_response` يتم بالاستعلام على `questions` بصلاحيات المالك (يرى كل
  الأسئلة حتى غير النشطة) لكنه **يرفض الرد على سؤال غير نشط** — آمن لأن التحقق
  يتجاهل طلبات الزائر الخبيثة.
- تسوية صغيرة: هذا يعني أن الزائر قد "يكتشف" وجود سؤال غير نشط عبر رسالة خطأ
  مختلفة. ليست ثغرة عملية (لا كشف محتوى).

## د) حذف البيانات

- حذف سؤال (عبر admin فقط) يظل محفوظًا في `response_answers` بسبب
  `ON DELETE SET NULL` + اللقطة.
- حذف استجابة (إدارية) يحذف إجاباتها ورافعاتها بواسطة CASCADE — سلوك مقصود
  لإدارة الحذف، لا للزائر.

## هـ) أنماط الاختراق المطروحة المراد تفاديها

| الهجوم | التصدي |
|---|---|
| الزائر يقرأ استجاباته/يعدّلها | لا SELECT/UPDATE للزائر؛ لا يملك معرفًا |
| الزائر يمنح نفسه admin | admin_users بلا RLS إدراج وبلا GRANT; bootstrap للمالك فقط |
| Search path hijack | `search_path=''` + مؤهّلات كاملة |
| SQL injection عبر القيم | نوع JSONB صارم + تحقق من نوع كل إجابة + cast محكوم |
| إغراق الحاوية | لا إدراج مباشر، حدود الحاوية، صلاحية زمنية، rate limit في Edge، تأكيد فعلي |
| قراءة ملفات خاصة | سياسة SELECT للمسؤولين فقط + حاوية خاصة |
| إرفاق token مرتين/سباق | شرط `response_id IS NULL` + `status='uploaded'` داخل `submit_response` |
| تجاوز الحد الأقصى للأسئلة العليا | حد 300 إجابة + قيود على أنواع المدخلات |

## و) حدود غير قابلة للحل في الخطة الحالية

- MIME spoofing كامنًا مهما كان التصميم (لا فحص ثنائيات محتوى في منصة Supabase
  Storage الجاهزة) — يُخفَّف بحدود حاوية + فحص النوع الفعلي في `confirm_upload`
  من metadata الكائن + حدود عرض عند التنزيل.
- لا يوجد rate limiting **على مستوى قاعدة البيانات**؛ التقييد الحالي «أفضل جهد»
  لكل مثيل Edge عبر `RATE_LIMIT_PER_MINUTE`. التقييد الحاسم لكل IP/نقطة يحتاج
  ضبطًا على بوابة المنصة.
- لا سجلات IP/جهاز للمشاركة في قاعدة البيانات (قرار تصميمي لصالح الخصوصية)؛
  ملاحظة: سجلات منصة Edge قد تحتوي IP لعملية التقييد — تُضبط مدة الاحتفاظ بها.
